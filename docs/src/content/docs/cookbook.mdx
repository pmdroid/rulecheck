Rulecheck v1 supports three matcher forms: **literal text**, **regex text**, and **forbidden path**. The first three recipes show those forms; the remaining recipes show how to control where they apply. The code below comes from the same TypeScript files that CI runs. Copy a recipe into `.rulecheck/rules/` and adapt its ID, paths, and fixtures.

From the repository root after building the CLI:

```sh
bash docs/examples/run.sh             # all recipes
bash docs/examples/run.sh path-globs  # one recipe
```

## Literal text

Ban an exact spelling. This is a case-sensitive substring check, not a parser: `legacy_mode=true` is different from `legacy_mode = true`. Use a regex if spacing should not matter.

## Excluded paths

Use `exclude` to drop files from a broad scope. A file is checked when it matches `paths` and nothing in `exclude`. Fixtures use the same scope, so add a fixture for each excluded area. Both lists are case-sensitive, which means `src/Generated/` is still in scope here. If a scope such as `**/*.ts` would also cover the rule sources, add `.rulecheck/**` to `exclude`.

## Multiple paths and exact locations

The entries in `paths` are alternatives. Here, both the core package and API service are checked; the web service is not. Literal matching reports only the first match per rule and file. Columns are one-based Unicode scalar positions, so the Greek letter before the match still counts as one column.

## Exact paths and advanced globs

Mix an exact repository-relative path with a pattern. This example uses `**` for recursive matching, `{private,local}` for alternatives, `[0-9]` for a character range, and `?` for one non-separator character. In the preceding forbidden-path recipe, `*` matches within one path segment. Use forward slashes in all path patterns.

## Reading fixture expectations

Use `expect: null` for a clean or out-of-scope example, or an exact `{ line, column }` for a finding. A text fixture must provide `content`; a forbidden-path fixture must omit it. The cookbook runner checks fixture expectations and then scans real tracked files. It also verifies exit 2 for an unsupported policy version.

These matchers do not parse an AST or understand whether text is inside a comment or a string. Use a language-aware linter or test for those checks.
