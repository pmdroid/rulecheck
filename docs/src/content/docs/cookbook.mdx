Rulecheck supports four matcher forms: **literal text**, **regex text**, **forbidden path**, and **syntax**. The first three recipes show the text and path forms, the middle recipes show how to control where a rule applies, and the [syntax recipes](#comments-in-function-bodies) select TypeScript, TSX and Rust syntax nodes. The code below comes from the same TypeScript files that CI runs. Copy a recipe into `.rulecheck/rules/` and adapt its ID, paths, and fixtures.

From your project's Git checkout root, run the installed CLI after copying and adapting a rule:

```sh
rulecheck test    # run the examples in the rule's fixtures
rulecheck check   # check the working-tree contents of tracked files
```

Use `git add` to stage new target files before checking them, or run `rulecheck check --untracked` to include non-ignored untracked files.

## Rule sources in a broad scope

In v1, rule sources under `.rulecheck/` are scan candidates like any other file, both in a working-tree check and with `--commit`. A rule's own file contains its pattern and fixture text, so a broad scope such as `**/*.ts` reports the rule itself. Add `exclude: [".rulecheck/**"]` to such a rule. Omitting rule sources automatically is deferred to a later contract version.

<Code code={ruleSources} lang="ts" title="rule-sources.rule.ts" />

The runner checks this recipe both ways. With the `exclude` entry removed, the same policy reports the rule file at its first match, the `pattern` value, in both modes:

```text
.rulecheck/rules/rule-sources.rule.ts:8:39: [source/no-debugger] Remove the debugger statement.
```

With the `exclude` entry, the same checkout is clean, and a `debugger;` in `scripts/release.ts` is still reported.

## Reading fixture expectations

Use `expect: null` for a clean or out-of-scope example, or an exact `{ line, column }` for a finding. A fixture expects at most one location because each rule reports at most one finding per file. A text fixture must provide `content`; a forbidden-path fixture must omit it. The cookbook runner checks fixture expectations and then scans real tracked files. It also verifies exit 2 for an unsupported policy version.

One finding per rule per file, at the first match, is the v1 contract for `check` and its JSON output. Fix that match and run the check again to see the next one. Reporting every match would change finding counts, so it is reserved for a later flag or contract version.

Text and forbidden-path matchers do not parse an AST or understand whether text is inside a comment or a string. Use a syntax rule when the difference matters.

## Comments in function bodies

A `syntax` rule parses each file in scope and reports the first node that its `selector` picks. This rule reports a comment anywhere inside a function body, including nested blocks, callbacks, class methods and JSX. A comment in a return type, a parameter list or at the top level isn't in a body, so it passes. `//` or `/* */` inside a string, template literal, regex literal or JSX text isn't a comment node, so it passes too. The `ignore` filters drop tool directives such as `// eslint-disable-next-line` and `// @ts-expect-error`, plus `TODO` and `FIXME` notes.

<Code code={syntax} lang="ts" title="syntax.rule.ts" />

The runner checks a clean checkout first. It has a file header comment, a `TODO` in a function body, and JSX text that starts with `//`. Then it adds a comment inside `total` and expects:

```text
src/total.ts:2:3: [source/no-function-body-comments] Move the explanation out of the function body or into a name.
```

A text regex for comment lines would also report the header, the `TODO` and a `//` line inside a template literal, and it would miss a trailing `return 1; // why`. The [syntax rule reference](../authoring/#syntax-rules) lists the selector fields and when a file cannot be judged.

## Reuse a selector

## Comments in Rust function bodies

The same selector works on Rust with `language: "rust"`, which parses `.rs` files. This rule reports a `//` comment anywhere inside the body of a function, method or closure, including nested blocks, `match` arms and macro arguments such as `vec![...]`. A comment in a return type, a parameter list or at the top level isn't in a body, so it passes, and so do `//!` and `///` docs on the item. `//` inside a string or raw string isn't a comment node. The `ignore` filters keep `// SAFETY:` comments, which Clippy's `undocumented_unsafe_blocks` lint asks for, and `TODO` and `FIXME` notes.

<Code code={syntaxRust} lang="ts" title="syntax-rust.rule.ts" />

The Rust grammar has two comment kinds: `line_comment` for `//`, `///` and `//!`, and `block_comment` for `/* */`. This rule selects `line_comment`, so a `/* */` in a body passes, as its last in-scope fixture shows. To report block comments too, add a second rule with `node: "block_comment"` and the same `inside`.

The runner checks a clean `src/lib.rs` first. It has crate and item docs, a `TODO`, `"// none"` in a string, and a `SAFETY` comment. Then it adds a comment inside `total` and expects:

```text
src/lib.rs:2:5: [source/no-rust-function-body-comments] Move the explanation out of the function body or into a name.
```
