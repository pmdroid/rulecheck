Rulecheck supports six matcher forms: **literal text**, **regex text**, **forbidden path**, **syntax**, **structured YAML** and cross-file **consistency**. The first three recipes show the text and path forms, the middle recipes show how to control where a rule applies and how to [keep two files in step](#keep-two-files-in-step), the [syntax recipes](#comments-in-function-bodies) select TypeScript, TSX, Rust, Go and Python syntax nodes, and the [structured recipes](#a-key-every-entry-must-declare) check keys and values in YAML files. The code below comes from the same TypeScript files that CI runs. Copy a recipe into `.rulecheck/rules/` and adapt its ID, paths, and fixtures.

From your project's Git checkout root, run the installed CLI after copying and adapting a rule:

```sh
rulecheck test    # run the examples in the rule's fixtures
rulecheck check   # check the working-tree contents of tracked files
```

Use `git add` to stage new target files before checking them, or run `rulecheck check --untracked` to include non-ignored untracked files.

## Forbidden path with an anchor

A forbidden-path rule can't tell an absent file from an absent directory. If `services/billing/` is renamed, a rule for `services/billing/config/*.local.toml` keeps passing while the forbidden file lands at the new path. Add `anchors`: globs for files that always exist next to the forbidden ones. When the forbidden file is absent and an anchor exists, the check passes as before. When no file matches any anchor, the check can't judge the rule and exits 2.

<Code code={pathAnchors} lang="ts" title="path-anchors.rule.ts" />

The runner checks a clean checkout and then the forbidden file, as in the other recipes. Then it moves `services/billing` to `services/payments` and expects exit 2 from the working tree and from the exact commit, with no findings and this on stderr:

```text
[config/no-service-overrides] missing anchor: no file matches the rule's anchors, so the area it guards moved or vanished and an absent forbidden path proves nothing; restore the anchor or update anchors and paths together
rulecheck: one or more forbidden-path rules found none of their anchors
```

Update `paths` and `anchors` together when you move the directory. Some rules have no natural anchor:

- **Repository-root paths** such as `docker-compose.override.yml` in the [glob recipe](#exact-paths-and-advanced-globs). The root can't move, so there's nothing to anchor. Leave `anchors` out.
- **Paths that are forbidden everywhere**, such as `**/*.pem` or `**/.env`. The rule guards no single directory, so an empty match is the clean result. Leave `anchors` out.
- **A directory with no file that always exists.** Anchor the closest file that does, such as the package manifest one level up (`services/billing/package.json`). Don't add a placeholder file only to anchor the rule unless the team will keep it.

An anchor must not match a fixture that expects a finding, because a forbidden file that is its own anchor could never pass. The builder and the evaluator reject `anchors` on text and syntax rules, which already exit 2 when no file is in their scope.

`anchors` doesn't change the matcher digest, so a [baseline](../baselines/) recorded before you add it still applies. Rulecheck releases from before `anchors` reject a policy that uses it as an unknown field (exit 2). Before you add it, make sure every evaluator that checks the repository, including the trusted base tools in CI, is a release that supports it.

## Reading fixture expectations

Use `expect: null` for a clean or out-of-scope example, or an exact `{ line, column }` for a finding. `expect` names at most one location because by default each rule reports at most one finding per file. To assert every match, use [`expectAll`](#count-every-match). A text fixture must provide `content`; a forbidden-path fixture must omit it. The cookbook runner checks fixture expectations and then scans real tracked files. It also verifies exit 2 for an unsupported policy version.

One finding per rule per file, at the first match, is the v1 default for `check` and its JSON output. Fix that match and run the check again to see the next one, or count every match with [`--all-matches`](#count-every-match).

Text and forbidden-path matchers do not parse an AST or understand whether text is inside a comment or a string. Use a syntax rule when the difference matters.

## Count every match

`rulecheck check --all-matches` reports every match of a text rule, not only the first per file. A fixture can assert all of those positions with `expectAll`, a list of `{ line, column }` in ascending order, in place of `expect`. An empty list expects no match. One rule can mix both kinds of fixture: `expect` checks the first match and `expectAll` checks every match.

<Code code={allMatches} lang="ts" title="all-matches.rule.ts" />

The runner checks a clean file first, where `TODOS` is not a whole-word marker. Then it adds two markers on line 1 and one on line 2. With `--all-matches`, the working tree and the exact commit both report:

```text
src/app.ts:1:4: [source/no-todo-markers] Resolve the marker or move it to the issue tracker.
src/app.ts:1:12: [source/no-todo-markers] Resolve the marker or move it to the issue tracker.
src/app.ts:2:11: [source/no-todo-markers] Resolve the marker or move it to the issue tracker.
```

Without the flag, the same file reports only `src/app.ts:1:4`. The `π` before `FIXME` counts as one column but two bytes, so in `--format json` the second finding has `byteStart` 12.

If the third fixture listed only the first two positions, `rulecheck test` would fail at the first difference and show both lists:

```text
src/app.ts:2:11: [source/no-todo-markers] fixture 3 expected 2 violations at 1:4, 1:12, found 3 violations at 1:4, 1:12, 2:11. Resolve the marker or move it to the issue tracker. Update the rule or fixture.
```

`expectAll` is for text rules. A forbidden-path rule reports at most one finding per path, and syntax rules aren't counted yet, so the builder and the evaluator reject `expectAll` there. The [CLI reference](../cli/#every-match) defines the match semantics for literal, regex and zero-width patterns.

## Require text in the same file

A text rule can be conditional: when its `pattern` matches a file, the file must also match `requires` somewhere. Here every file under `src/` that starts an interval must also clear one. The requirement can come before or after the trigger and on any line. Text in another file doesn't count.

<Code code={requires} lang="ts" title="requires.rule.ts" />

Findings point at the trigger, the `pattern` match, and never at the requirement. A file without a trigger is clean, and so is a file with both. A file with triggers and no requirement reports its first trigger by default, or every trigger with `--all-matches` and in a [baseline](../baselines/). The runner checks a clean checkout, then drops `clearInterval` from `src/poll.ts`. The working tree and the exact commit then both report:

```text
src/poll.ts:1:12: [source/interval-needs-clear] Keep the interval handle and call clearInterval when the work stops.
```

`requires` takes the same `{ kind, value }` as `pattern`, and only text rules have it. A regex requirement that can match empty text, such as `x*` or `(clearInterval\()?`, is refused when the policy loads, because every file would meet it and the rule could never report. The requirement is file-wide presence only. It doesn't tie a trigger to a nearby match or to the same function. A file whose text can't be read as UTF-8, or a scoped path that can't be read without following a symlink, exits 2 and doesn't count as meeting the requirement.

## Keep two files in step

A `consistency` rule relates files instead of judging each one alone. Its `paths`, `exclude` and `excludeSets` select an inventory, and each named scope inside it extracts values with a regex that has one capture group. The `same-values` form reports every value that one scope has and the other lacks. Here every flag documented in `docs/flags.md` must be a key in `config/flags/*.json`, and the other way round.

<Code code={consistencySameValues} lang="ts" title="consistency-same-values.rule.ts" />

A consistency fixture lists a small inventory in `files` and every finding in `expectFindings`, ordered by path and location. The runner checks a clean checkout, then adds an undocumented `dark_mode` key to `config/flags/a.json`. The working tree and the exact commit then both report it where it is configured, with a detail that names both scopes:

```text
config/flags/a.json:1:25: [docs/flags-match-config] "dark_mode" is in configured but not in documented. Document every configured flag in docs/flags.md and remove entries for flags that are gone.
```

Each captured value is trimmed of surrounding whitespace. An empty value is dropped, and a value repeated across files counts once, so it's reported once, at its first occurrence by path and position. Values are compared byte for byte: case, Unicode normalization and quoting aren't changed, so write the regex to capture exactly the text that should match.

## Check that listed files exist

The `path-exists` form reads references from one scope and reports each one that doesn't name a regular file of the rule's inventory. With `base: "file"` a reference is relative to the directory of the file it's in, and with `base: "root"` it's relative to the repository root.

<Code code={consistencyPathExists} lang="ts" title="consistency-path-exists.rule.ts" />

The runner checks a clean checkout, then lists a file that doesn't exist. Both check modes report:

```text
assets/manifest.txt:2:7: [assets/manifest-files-exist] "icons/gone.svg" resolves to assets/icons/gone.svg, which is not in the selected inventory. Add the missing asset or remove its line from assets/manifest.txt.
```

A reference is resolved as text and never opened: `.` segments are dropped and `..` steps up one directory. A reference that is absolute, contains a backslash, a control character, an empty segment or `.git`, or climbs above the repository root is reported as escaping the repository instead of being looked up. A file outside the rule's `paths`, a deleted file and a symlink are never in the inventory.

Both forms are bounded and judge the same inventory in a working tree and in an exact commit:

- A scope that matches no file can't be judged, so the check exits 2. A scope whose files hold no values is judged and has an empty set.
- A symlink or submodule in the rule's scope exits 2 in both modes. Exclude it, or narrow `paths`.
- Each scope extracts at most 10,000 values of at most 1,024 bytes. More exits 2. In a finding's message each value is escaped and cut to 64 characters, like a [message template](../authoring/#per-finding-messages) capture.
- After a [text budget](../cli/) stop the rule reports nothing and is listed as not evaluated, since a later file could change its result.
- `skipIfContent` and `anchors` don't apply. Consistency rules don't join more than two scopes, don't compare snippets, and run no repository code.

## Comments in function bodies

A `syntax` rule parses each file in scope and reports the first node that its `selector` picks. This rule reports a comment anywhere inside a function body, including nested blocks, callbacks, class methods and JSX. A comment in a return type, a parameter list or at the top level isn't in a body, so it passes. `//` or `/* */` inside a string, template literal, regex literal or JSX text isn't a comment node, so it passes too. The `ignore` filters drop tool directives such as `// eslint-disable-next-line` and `// @ts-expect-error`, plus `TODO` and `FIXME` notes.

<Code code={syntax} lang="ts" title="syntax.rule.ts" />

The runner checks a clean checkout first. It has a file header comment, a `TODO` in a function body, and JSX text that starts with `//`. Then it adds a comment inside `total` and expects:

```text

```

A text regex for comment lines would also report the header, the `TODO` and a `//` line inside a template literal, and it would miss a trailing `return 1; // why`. The [syntax rule reference](../authoring/#syntax-rules) lists the selector fields and when a file cannot be judged.

## Comments in Rust function bodies

The same selector works on Rust with `language: "rust"`, which parses `.rs` files. The `ignore` filters keep `// SAFETY:` comments, which Clippy's `undocumented_unsafe_blocks` lint asks for, and `TODO` and `FIXME` notes.

<Code code={syntaxRust} lang="ts" title="syntax-rust.rule.ts" />

## Comments in Python functions

With `language: "python"`, the selector parses `.py` and `.pyi` files. This rule reports a `#` comment anywhere inside a function definition, including nested blocks and methods. Module and class-level comments, decorator-line comments and the shebang pass. `#` inside a string, an f-string or a docstring isn't a comment node. The `ignore` filters keep `# noqa`, `# type:`, `# pragma:`, `# pyright:` and `# mypy:` directives and `TODO` and `FIXME` notes.

<Code code={syntaxPython} lang="ts" title="syntax-python.rule.ts" />

The Python grammar attaches a comment that comes before a function's first statement to the `function_definition` node, not to its `body` block. With `field: "body"`, a selector would miss the comment in the first fixture, so this rule names only the kind. That means a comment in the parameter list or on the `def` line counts too, as the fifth fixture shows. A comment before the first statement of a nested `if` or `for` belongs to that statement, so it is still inside the function.

The runner checks a clean `src/app/total.py` first. It has a module comment, a docstring and a string with `#`, a `TODO` and a `# type: ignore`. Then it adds a comment as the first line of `total` and expects:

```text
src/app/total.py:2:5: [source/no-python-function-comments] Move the explanation into a docstring or a name.
```

## A forbidden YAML value

`not-equals` reports a selected scalar with the given text. This rule reports `contents: write` under the top-level `permissions`, whether the value is quoted or not. A missing `permissions` block, other keys and job-level permissions select nothing, so they pass.

<Code code={structuredYamlValue} lang="ts" title="structured-yaml-value.rule.ts" />

```text
.github/workflows/release.yml:3:13: [ci/no-contents-write] Grant contents: write only to the job that needs it, or use read.
```
